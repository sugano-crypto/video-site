# 閲覧権限補強の候補（本番未適用）

`index.candidate.html` は表示修正PR #1のHTMLに、カタログRPC・記事を開く時の再認可・署名メディアを追加した候補です。現在公開中のHTMLを変更していません。
再生成：`python member-access/build-candidate.py <PR1のindex.html> member-access/index.candidate.html`。

対応するサーバー：
- `sql/004-member-access-candidate.sql`：契約・会員区分・公開状態による記事RLS、本文をマスクするカタログ、記事単位の取得RPC、会員情報の自己昇格防止トリガー。
- `functions/article-media-links/`：JWTをSupabase Authで検証し、呼び出しユーザーのRLSで対象記事を確認してからカバー/MP3の署名URLを発行。TTLは5分、ブラウザは4分で再確認・更新。GitHub PagesのCORSプリフライトにも対応。
- `functions/sync-notion-articles/`：既存名の入口を専用認証付きの安全な処理へ置換する候補。旧URLを認証・削除保護なしで残さないためのもの。未デプロイ。

会員の一覧・無料部分は残し、有料本文/blocks/メディアURLは契約中で対象区分に合う会員だけに返します。現行と同様、管理者は全記事を扱えます。契約終了は一覧から除外します。契約日付による追加ルールは推測せず、現行のcontract_status判定に合わせています。
本人が更新できる会員情報は、自分のis_first_loginをfalseへ変更する処理だけに制限する候補です。管理者/サービスの会員管理は維持します。動画・動画権限のコード/テーブルは変更しません。

採用前に必要な確認：user_profilesの列/RLS/既存トリガーとの互換性、articles.idの採番方式、本番データの公開区分値、実ユーザーによる管理操作/動画/MP3の動作。
資料 `sql/003-inspect-membership-readonly.sql` は準備済みですが、ユーザーへ追加操作は依頼していません。これらの不明点は本番適用の保留条件です。

## 同時切替が必要

1. バックアップと検証環境でのテスト。非公開SQLだけを先に本番で適用しない。
2. 新しいRPC/認可付きメディア関数を準備し、既存・新同期入口を専用認証へ揃える。
3. 新HTMLをテストし、正しい権限で画像・MP3が再生できることを確認。
4. 承認した切替時間に、HTML・記事RLS・会員ガード・Storage private化・Cronを揃える。公開バケットを非公開にするSQLは含めていない。
5. 新同期のapplyは、環境変数の許可、リクエストの許可、サーバー側準備確認の3条件を満たした場合だけ動く。DB準備確認は記事RLS・会員ガード・article-mediaのprivate化をチェックする。

公開バケットの切替後も、DBに保存された従来のpublic形式URLはオブジェクトの場所を示す情報として維持し、メディア関数が署名URLへ変換します。データやファイルを削除する必要はありません。
カバー/上部MP3以外のNotion本文内メディアや外部リンクには別の公開設定があるため、この候補だけで全外部リンクが保護されるとは扱いません。
短い署名URLでも、発行済みURLは期限まで使用でき、すでに取得した本文やファイルは回収できません。
