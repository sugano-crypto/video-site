# 提供CSVに基づく権限確認と追加の移行条件

2026年10月18日。ユーザーがSQL Editorで読み取り調査した25行のCSVを確認した。本番APIのアクセス試験、同期実行、権限変更は行っていない。

## 確認できた事実

- articles は19列。id は bigint、published_at は date、price は bigint、notion_page_id は text。notion_blocks は jsonb。
- idがPRIMARY KEY、article_idとnotion_page_idがそれぞれUNIQUE。
- articles のRLSは有効（FORCEは無効）。返されたSELECTポリシーは authenticated に対して `USING (true)` の1件。
- このポリシーは契約状態・会員区分・status・有料区分による行制限をしない。通常の会員画面で記事を取得できていることと合わせると、画面のロック判定だけではAPI経由の本文取得を防げない。
- RLSは行の制限であり、このポリシーでは無料部分と有料本文の列を分離していない。RLS有効という表示だけでは、有料本文の権限保護が成立しているとはいえない。
- article-media はpublic=true。URLを知る人は、公開オブジェクト取得経路からログインなしでファイルを取得できる。StorageのSELECTポリシーが結果に出なくても、この公開取得は制限されない。公開設定だけでファイル名一覧を誰でも取得できると断定はしない。
- articlesの非内部トリガーは結果にない。user_profilesのポリシー・列権限・トリガーは今回の調査対象外。
- id のcolumn_defaultはnullだが、これはIDENTITYがない証明ではない。is_identity/identity_generationを追加確認する。
- status の既定値はnull。access_typeは'free'、target_audienceは'all'、note_statusは'unpublished'。現在入っている値の種類は未確認。

## 今回の候補への反映

ローカルDBテストをCSVの列型・既定値・UNIQUE制約に合わせた。idの採番だけは「BY DEFAULT IDENTITY」を仮置きしており、未確認の前提として明記した。
同期SQLは `public.articles` の実record型を使うため、そのSQL自体にuuid型のid依存はなかった。
同一本文ページを指す複数の新規記事を事前に止め、既存の別記事とnotion_page_idが衝突するときもメディア保存前に停止するよう同期コードを補強した。

Node 16件＋ローカルPostgreSQL 7件＝23件成功。UNIQUE衝突時の元記事・同期状態保持を検証した。
また、CSVと同じUSING(true)ポリシーのテスト用DBで、SELECT権限を持つauthenticatedが有料本文を取得できることを再現した。本番の会員になりすましたアクセス試験はしていない。

## 対策案（本番移行前に追加設計・テストする）

1. user_profilesの契約区分・会員種別を一般会員が書き換えられないことを確認する。自己更新のRLSだけでは更新可能な列を制限できない。管理者による会員管理と、本人による初回パスワード変更の更新を維持しつつ、必要なら列権限・限定RPCで分ける。
2. 記事の一覧用データと、有料本文・notion_blocks・メディアの取得を分ける。一覧の表示を保ち、本文を返すサーバー側では毎回auth.uid、契約状態、会員区分、記事公開状態を検証する。テーブルへの直接取得経路も同じ制限を満たすようRLS/列権限を整える。
3. 管理者判定は画面変数でなく、サーバー側で検証する。既存管理者の全記事・会員管理権限を維持する。記事と独立した動画権限を変更しない。
4. 画像・MP3は、権限確認後に短時間の署名URLを発行する方式を検討する。まず閲覧側に署名URL対応を追加して検証し、公開バケットの切り替えはその後にする。先にpublic=falseだけを適用しない。
5. 既存の公開URLを残したまま別の非公開バケットへコピーしても、元の公開URLは保護されない。全既存経路を移行した後の公開アクセス停止までを計画し、原本の削除は不要な方法を優先する。
6. 本文中のNotion画像/音声URLや公開Notionリンクも、必要な範囲で保護方針を確認する。カバーと上部MP3だけを保護して全メディアが保護されたとはしない。
7. Notionで明示的に非公開へ戻した場合は、同期所有範囲だけのstatusを更新し、サーバー側の本文・署名URL発行を止める。ソースからの欠落や403/429/タイムアウトを非公開化と混同しない。
8. 署名URLは有効期限内は再利用できるため、短いTTLと音声の再生/シーク時更新を設計する。公開取り消し後にも残るTTLの上限を明示する。

この権限問題は今回のCSVで確認された既存状態であり、今回の表示/同期提案が新たに導入したものではない。修正は未適用。表示PR/同期PRのテスト成功を、本番有料アクセスの安全性の証明として扱わない。

## 次に必要な読み取り確認

`sql/003-inspect-membership-readonly.sql` は会員テーブルの構造・権限・トリガー、articles.idの採番方式、記事公開区分の件数集計のみを返す。会員レコード、記事本文、秘密キーは取得しない。
